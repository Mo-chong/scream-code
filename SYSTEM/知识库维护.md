> 定义什么内容适合放入 knowledge 系统、什么不适合、以及最佳实践。

## §1 能力基线 [P0]

### 1.1 搜索是怎么找到内容的？

```
query → [1] LLM提取实体名 → [2] entityRecall(精确名匹配+向量0.5)
       → [3] seedEvents(实体→事件 + 标题向量0.4)
       → [4] BFS 1 hop(事件→实体→邻居事件, 上限100)
       → [5] coarseRank(cosine相似度, 取50个候选)
       → [6] LLM rerank(精确排序, 取topK≤20)
       → [7] 回填(不足时chunk向量补)
```

**结论：搜索靠"实体"起跳。** 没有实体/实体不可识别的文档，直接跳过步骤[2][3][4]，掉到[7] chunk向量搜索——本质退化为纯 embedding 模糊匹配。

### 1.2 文档在摄入时经历了什么？

| 阶段 | 对文档的要求 |
|------|------------|
| 分块 | `.md`→按标题分割；`.txt`→按空行分割。无标题的文本段落式分块，丢失层级 |
| 清洗 | `stripMarkdown()` 删除代码块/行内代码/图片/链接/加粗标记。纯代码文档被大幅抽空 |
| LLM提取 | 每 chunk 提取 1 个 event + 2-6 个 entity。无实体的 chunk 生成空 entity 列表 |
| 去重 | entity 去重键 `type\|name_lowercase`，per chunk 内去重，非全局跨文档融合 |
| 存储 | 增量式追加，无文档更新机制。改文档内容必须删 source 重来 |

### 1.3 系统明确做不到的

| 不能做的事 | 为什么 |
|-----------|--------|
| entity↔entity 直接关系 | 只有 `event_entities` 表——实体之间无边 |
| 跨 source 的实体融合 | UNIQUE 约束含 `source_id`，同名实体不同源各自独立 |
| 多跳推理（>1 hop） | BFS 严格 1 跳，`EXPANDED_EVENT_LIMIT=100` 硬上限 |
| 精确布尔查询 | 无 tag 过滤/日期范围/类型过滤作为搜索参数 |
| 位图/反排/数值范围 | 仅 FTS5 全文 + cosine 余弦相似度 |
| 增量更新 | `ingestContent` 是 append-only |
| 大文件（>200 chunk） | LLM 串行提取每个 chunk，O(n) 耗时爆炸 |
| 图片/PDF 原生提取 | 无多模态支持，需外部转 text 后摄入 |

## §2 分档矩阵 [P0]

### 2.1 档位定义

| 档位 | 定义 | 搜索表现 | 系统负担 |
|------|------|---------|---------|
| **⭐⭐ 高** | 系统能力全覆盖，检索精度高 | 实体→BFS→rerank 全链路有效 | 摄入成本合理 |
| **⭐ 中** | 部分能力有效，降级后也够用 | 掉到 FTS5 或 chunk 向量但仍能搜到 | 摄入/存储中等 |
| **○ 低** | 系统优势用不上，搜索结果差 | 跌到三级降级 | 存储/LLM 成本浪费 |
| **✕ 不能放** | 系统无法正确处理或有害 | 搜不到/搜错/系统崩溃 | 系统层面冲突 |

### 2.2 ⭐⭐ 高价值（强烈建议放入）

#### 带标题层级的技术文档

- 类型：MD/ADRs/API 参考/架构设计/开发规范
- 示例：`SYSTEM/*.md`、protobuf 定义文档、内部框架文档
- 原因：
  - 标题结构 → `chunkMarkdown()` 按 `##` `###` 精准分块，保留 `heading` 元数据
  - 实体密度高：产品名(`product`)、组织(`organization`)、概念(`subject`)、指标(`metric`)
  - 实体类型匹配 11 种枚举——LLM 提取准确率高
  - entityRecall + BFS 1 hop 跨 chunk 关联（"A 模块引用了 B 服务"）
  - LLM rerank 能区分 "MCP 协议介绍" vs "MCP 协议安全限制"
- 格式要求：Markdown，有 `##`/`###` 标题层级，正文含命名实体
- 注意：纯表格文档（无实体）→ 降为 ⭐ 中

#### 项目决策记录（ADR）

- 类型：`DECISIONS/ADR-N-标题.md`
- 原因：
  - 天然带实体：决策者(`person`)、技术选型(`product`)、团队(`organization`)、时间(`time`)
  - 实体间事件关系明确（"2024-06 决定用 SQLite 替代 PostgreSQL"）
  - 搜索"为什么选了 X" → entityRecall(X 作为 product) → 找到 seed events → BFS 展开关联决策
- 典型查询全链路：查询"postgres 迁移原因" → LLM 提取 `[product:postgres]` → 精确匹配 entity → 种子事件 → BFS → cosine → rerank

#### 技术调研报告

- 类型：`DECISIONS/调研-*` / `DECISIONS/研-*`
- 原因：
  - 原理同 ADR，但通常更长、实体更多
  - 对比分析天然产生 `work`(论文/产品) + `metric`(数据) + `organization`(公司)
  - 事件 `category: comparison / decision` 丰富 rerank 信号

#### 框架/库用户指南

- 类型：外部文档的驯化版
- 原因：
  - 函数名/API名 → ENTITY_TYPE=`product`
  - 配置项 → ENTITY_TYPE=`subject`
  - 版本号 → ENTITY_TYPE=`time`
  - 示例代码但不被 strip（指南用文字描述代码，不是纯代码块）
- 边界：如果全是代码块无正文 → 降为 ⭐ 中

#### 带有命名实体的会议/讨论记录

- 类型：讨论总结（含人/组织/决定/时间线）
- 原因：多人 + 组织 + 决策 → entity 富集，易触发 entityRecall

### 2.3 ⭐ 中价值（可以放但收益有限）

#### 纯代码文件（源码）

- 问题链：
  - `chunkMarkdown()` 不适用（无标题）→ 用 `chunkText()` 按空行分块 → 无层级
  - `stripMarkdown()` 对普通代码不生效（无代码 fence）→ 但 LLM 提取 entity 困难（函数名→`metric`? `action`? 不确定）
  - entity 类型枚举不覆盖 `class`/`function`/`variable` → 提取为 `subject` 或跳过
  - 用户查询"查 XX 函数的实现" → LLM 从 query 中提取 entity("XX") → entityRecall 大概率匹配不上（函数名不在 entity 表）
- 实际表现：直接走 chunkVectorFallback → embedding 相似度 + FTS5 → 勉强能搜
- 建议：只有关键模块的核心源码值得放，且期望值降低。不如用 Memory 存"这段代码干什么用"

#### 纯概念定义（无实体）

- 类型：纯理论说明，如"什么是递归"
- 问题链：内容只有 `subject` 类型 entity（递归本身）→ entityRecall 精确匹配可能命中 → 但 BFS 无展开（无其他 entity 可关联）→ 直接跳 chunkVectorFallback
- 建议：可以放，但不如直接放带例子的教程（含实体 `product` `organization` 等）

#### TODO / 清单 / 简单日志

- 问题链：实体极少 → chunk 无 event 价值 → 填充 entity 可能被 LLM 跳过
- 建议：适合放但价值天花板低。更建议用 Memory 存任务状态

#### 外部引用文档（语言不一致）

- 问题链：
  - LLM extraction prompt: "Output language must follow the main input language"
  - 中文 query 搜英文文档 → entity 匹配失败（normalized_name 不一致）
  - 掉到 chunkVectorFallback + FTS5 → 可能仍能搜到
- 建议：仅当知识库使用语言和目标查询语言一致时放入

#### 自助格式文档（非 `.md`/`.txt`）

- 类型：`.yaml` `.json` `.csv` `.pdf`
- 问题链：没有原生 extractor 支持，需外部预处理
- 建议：转 text 后可放，但结构丢失严重

### 2.4 ○ 低价值（不推荐放）

#### 纯数据表 / 多维数据集

- 类型：CSV 导出、stats 报表、埋点数据
- 原因：
  - 无标题层级 → chunkText() 按空行分块，可能一块就是整个文件
  - 无命名实体（数字/指标在 ENTITY_TYPE `metric`，但 LLM 对单纯数字不提取）
  - 查询"2024年Q3的转化率" → entityRecall 精确匹配不到（数值不存为 entity）
  - FTS5 keyword 匹配可能 OK，但代价是全表扫描
- 结论：知识库不适合存表格数据。用数据库/电子表格

#### 纯图片/截图（无可读文本）

- 原因：store 只存 TEXT/BLOB 类型文本，无多模态支持
- 例外：截图转文字后可放，但质量取决于 OCR

#### 重复性高的模板文档

- 类型：PRD 模板、邮件模板、会议邀请模板
- 原因：多数 chunk embedding 高度相似 → coarseRank cosine 区分度低；entity 几乎一样
- 结论：放 1 份模板就够了

#### 纯日志 / changelog / release notes

- 类型：逐条记录型文档
- 原因：每条日志独立无交叉实体 → BFS 1 hop 无扩展价值；`time` entity 极多容易触发 seedEvents 截断(30上限)
- 结论：可放关键版本说明，完整 changelog 性价比低

#### 小于 100 字符的碎片笔记

- 原因：分块后只有 1 个 chunk；LLM 提取 entity 列表可能为空；搜索命中依赖 FTS5
- 结论：直接用 Memory 存更经济（无 LLM extraction 开销）

### 2.5 ✕ 绝对不能放

#### 机密 / PII / 凭据

| 内容 | 危险原因 |
|------|---------|
| 密码/API key/Token | LLM 可能提取为 entity → 明文存在 SQLite 中 |
| 身份证/手机号/邮箱 | extractor prompt 要求提取"clear entities" → 可能被提取 |
| 商业机密文档 | 知识库无权限控制，任何有 KnowledgeLookup 权限的 agent 可查 |

- 行为：`store.findEntitiesByName()` 精确匹配 → 任何 Agent 可通过 `/knowledge` 或 KnowledgeLookup 搜索
- 结论：**严禁放入**。用加密存储

#### 需要精确版本管理/时间旅行的文档

- 类型：合同条款多版本、上线清单、频繁修改的规范文档
- 原因：无增量更新 → 每次修改需 deleteSource + re-ingest，且旧数据残留
- 结论：用 git + gitbook

#### 需要精确过滤的文档

- 类型：法律条款搜索（"第 7 条第 2 款"）、合规检查清单（"检查项 3.2.1"）、代码版本定点查询（"v3.2.0 的 API 变更"）
- 原因：FTS5 tokenizer 分词后无法精确位置匹配；embedding 更模糊
- 结论：不适合精确/结构化查询场景

#### 需要多跳推理的知识领域

| 领域 | 为什么不行 | 系统限制 |
|------|-----------|---------|
| 医学诊断推理（A症状→B疾病→C用药） | BFS 只有 1 跳 | `EXPANDED_EVENT_LIMIT=100` |
| 复杂系统故障树 | 因果链通常 3-6 层 | 系统无图遍历能力 |
| 供应链溯源 | 需要多级跳转 | entity↔entity 无直接边 |

- 结论：系统设计就是文档知识库，不是推理引擎。多跳推理用专门的知识图谱

#### 大文件（>200 个 chunk）

- 原因：
  - LLM extraction 串行（concurrency=3 per chunk）→ 200 chunks 约 67 轮 LLM 调用
  - 搜索时 entityRecall 可能召回数十个 entity → seedEvents 截断(30上限)
  - 粗排 50 个候选中有 30 个来自同文件 → LLM rerank 失去多样性
- 建议：按主题拆成多个小文件（每个 10-30 个 chunk 最优）

#### 非自然语言内容

| 内容 | 原因 |
|------|------|
| 纯 JSON Schema | 无自然语言实体，LLM extraction prompt 不适用 |
| 二进制 protobuf 描述 | 同上 |
| SVG/LaTeX 源码 | 同上，embedding 在符号空间无意义 |
| 数学证明/公式集 | entity 类型不覆盖数学符号 |

- 结论：不是 NLP 系统做不了

## §3 放入前自检清单 [P1]

```
□ 文档有标题层级？ (##/###)
□ 包含 ≥3 个命名实体 (人/组织/产品/概念)
□ 实体类型在 [person|org|location|product|subject|metric|work|...] 内？
□ 文档长度在 5-200 个 chunk 之间？
□ 内容更新频率 ≤ 月级？
□ 不需要精确匹配/版本追踪？
□ 没有密码/key/PII？
□ 目标查询语言与文档语言一致？
```

- 全部 ✅ → ⭐⭐ 高价值
- ≥4 ✅ → ⭐ 中价值
- ≤2 ✅ → ○ 低价值
- 任一关键否决 → ✕ 不能放

## §4 替代方案映射 [P1]

| 不适合知识库的场景 | 替代方案 |
|------------------|---------|
| 少量碎片笔记（<100字符） | Memory / MemoryWrite |
| 频繁更新的任务状态 | Memory（支持 /dream 清理） |
| 精确结构化查询 | SQLite / 数据库 |
| 多跳推理需求 | 专用知识图谱（Neo4j 等） |
| 机密/PII | 加密存储/密码管理器 |
| 版本化文档 | Git + GitBook |
| 大文件（>200 chunk） | 拆分成独立小文件 |
| 非文本/符号内容 | 不宜放入任何语言模型系统 |

## §5 维护规则 [P2]

- 文档更新频率：每季度或 knowledge 包有重大变更时复审
- 分档调整：如果搜索算法升级（例如增加 BFS 跳数），重新评估 §2 分档
- 新增内容：放入前过一遍 §3 自检清单
- 源码变更联动：`packages/knowledge/src/` 中 `search.ts`/`ingest.ts`/`chunking.ts` 的算法变化直接影响本文档的准确性
